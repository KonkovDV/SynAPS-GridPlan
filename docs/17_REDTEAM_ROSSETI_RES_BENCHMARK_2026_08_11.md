## 3. Что узнали при построении (технические уроки)

1. **Адаптер: due = конец ПЕРВОГО окна.** Для interruption-работ `release/due`
   берутся из первого одобренного окна (`min(allowed, start)`). Поздние окна
   для GREED не существуют — только для пост-чекера. Последствие: цепочка
   (ТО→испытания) должна целиком помещаться в первое окно актива, а первые
   окна активов одной бригады — в разные дни. Это не баг, но **семантику надо
   документировать** для будущих инстансов.
2. **GREED не знает о containment в окна** — только release/due. Плотная
   упаковка календаря бригады выталкивает хвост цепочки за окно. На демо-
   инстансе лечится разнесением окон; в продукте — кандидат на hard-констрейнт
   (см. п. 4).
3. **Stale-install рецидив**: hatchling editable на Windows материализует
   копию в site-packages — после `git pull` бенчмарк молча гонял 0.1.4.
   Правило: `pip install -e . --force-reinstall` + проверка версии (в README).

## 4. Открытые риски / атаки жюри

- **«Окна подогнаны под солвер»** — отчасти правда: первые окна разнесены
  вручную, потому что containment — пост-чек, а не hard-констрейнт. Ответ:
  честно показать это как roadmap-фичу «window-containment в ядро»; fail-closed
  чекер уже сегодня не даёт выдать битый план за хороший.
- **«Churn=0 — ремонт ничего не сделал»** — сорванные работы вернулись в прежние
  слоты: это свойство стабильности, в отчёте объяснено. Дополнительно: нет
  «якоря now» — repair пересобирает от начала горизонта (задокументировано в
  отчёте, кандидат на API `now_anchor`).
- **«Это данные Россетей?»** — нет, модель по открытым источникам; рамка
  `synthetic_experiment` в отчёте, JSON и README.
- **Upstream**: `IncrementalRepair` игнорирует `release_date` оконных работ
  (из 0.1.5) — демо срывает только не-оконные работы.

## Addendum (0.1.6): сценарий D — точный CP-SAT vs эвристика

Закрыт главный открытый риск «оптимальность не заявляется»: прогон инстанса
через CP-SAT (strict determinism, seed 42, 1 worker). Факты из прогона
(`rosseti_res_results.json`, воспроизводимо тестом
`test_res_cpsat_proves_optimal_makespan`):

- Статус **OPTIMAL**, `determinism_violated=False`, два прогона — идентичные.
- Dual bound = 30 600 мин = достигнутый горизонт → горизонт доказанно оптимален
  (LP-релаксация внутри CP-SAT; якоря: arXiv:2607.05177 «dual bound =
  certified optimality gap», arXiv:2506.04274 — CP-SAT на уровне точных
  BIP/B&B).
- GREED: gap 0% по горизонту и просрочкам; по вторичному критерию (переезды)
  1395 vs 810 мин — честная «цена скорости» x1.72.

Оставшиеся атаки жюри:

- «Инстанс мал — на реальном РЭС CP-SAT не докажет за 30 с». Честно: тогда
  публикуем dual bound (коридор «не хуже X% от оптимума») — продуктовое
  преимущество перед метаэвристиками без границ.
- «Big-M скаляризация маскирует многокритериальность». SynAPS публикует
  `objective_components` и `scalarized_objective_bound` раздельно, единицы
  bound подписаны (`objective_bound_units`) — утечка «минуты vs условные
  единицы» закрыта на уровне движка (Q3-аудит upstream).
- Вторичный gap GREED — не баг: приоритет эвристики — допустимость и горизонт;
  для экономии моточасов есть режим CP-SAT/LBBD.
